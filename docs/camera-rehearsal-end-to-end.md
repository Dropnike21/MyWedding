# End-to-end guest camera rehearsal

## What this tests

The test workflow covers the actual guest path:

**Owner generates a private rehearsal code → guest opens the invitation landing
page → guest taps Open your wedding camera → Firebase anonymously authenticates
the device → callable Function redeems the HMAC-protected code → camera
captures separate clean RAW and edited/watermarked JPEGs → two resumable Google
Drive uploads complete → Function verifies both Drive files → one frame is
consumed by a Firestore transaction → audit row is added to Google Sheets →
the private Wedding Studio Photo archive shows the committed test frame.**

The optional test mode shares the production upload implementation, but **never
opens the real wedding-day camera schedule** or changes real guest invitations.

All camera UI stays in **portrait layout**, even when a phone's browser viewport
turns landscape. The webpage cannot force the phone's operating system to
remain portrait; the portrait UI can scroll in a sideways browser viewport.

## Important activation status

The repository contains source code, **not a confirmed running Firebase
deployment**. Merging into GitHub does not deploy Cloud Functions, create
secrets, enable anonymous authentication, configure App Check, or authorize
Google Drive. Until that setup is completed, the landing-page design can be
previewed but **a live rehearsal upload cannot be verified**.

Never put Firebase Admin credentials, HMAC secrets, OAuth client secrets or
Google refresh tokens in the frontend, in GitHub, or in a chat message.

## One-time backend prerequisites (project: mywedding-1ad09)

1. Confirm Firebase **Blaze billing** and Cloud Functions are available for
   `asia-southeast1`. Check that Firebase Authentication → Sign-in methods
   includes **Anonymous** and the two organizer Google accounts are authorized
   through the existing verified-email allowlist.
2. Confirm reCAPTCHA Enterprise **App Check** for the GitHub Pages host
   `dropnike21.github.io`, using the public site key already configured in
   `assets/guest-config.js`. Test actual browser tokens before enforcing.
3. Prepare the Google account authorized to access the private wedding RAW
   folder, WATERMARKED folder, parent folder and photo audit spreadsheet.
   Obtain an OAuth refresh token with suitable Drive and Sheets permissions.
   Store a JSON secret with keys `clientId`, `clientSecret`, `refreshToken`.
4. In a trusted local terminal with Firebase CLI, from a checked-out
   `Dropnike21/MyWedding` repository:

   ```sh
   npm install --prefix functions
   firebase login
   firebase functions:secrets:set INVITATION_CODE_HMAC_KEY --project mywedding-1ad09
   firebase functions:secrets:set GOOGLE_DRIVE_OAUTH --project mywedding-1ad09
   firebase deploy --only functions --project mywedding-1ad09
   ```

   For the HMAC key, use a unique high-entropy random secret, e.g.
   `openssl rand -hex 32`, and paste it at the private CLI prompt. Do not
   rotate it casually after issuing codes. For `GOOGLE_DRIVE_OAUTH`, provide
   the complete JSON in the private CLI prompt. **No OAuth secret belongs
   in GitHub Pages.**

5. Check **Functions logs** for runtime errors, function availability and
   Google API permissions. In Planning Studio → Photo archive, the existing
   **Private storage** diagnostic should report connected folders and Sheet.

## First test on a phone

1. To see the invitation design without any live backend, open:
   `https://dropnike21.github.io/MyWedding/#camera/AJ27TEST`
   Select **Open your wedding camera** to enter the local-only test preview.
   This sample does **not** upload files or count real frames.
2. In **Planning Studio** sign in as an owner; open **Photo archive**.
   Select **Start 1-hour test**. Confirm the start succeeds.
3. Select **Generate test invitation link**. A **five-frame**, single-invitation
   code is generated by the protected backend and shown **once**. Copy the full
   URL (which includes `?cameraRehearsal=1#camera/<code>`), and open it in
   another browser/device.
4. Confirm the landing card displays A&J, December 23, 2027, an explicit
   **CAMERA REHEARSAL** badge, and a **private camera pass**. It should **not**
   activate the camera until you tap the guest CTA.
5. Tap **Open your wedding camera**. Confirm Firebase grants a guest session,
   then open the live camera and take a **non-sensitive test photo**. Wait
   for **Saved to private Drive**.
6. Check your Drive **RAW** and **WATERMARKED** folders: both JPEGs should
   exist, prefixed `TEST_AJ_`. The wedding copy should contain filters and
   the corrected date watermark; the RAW should be unfiltered.
7. In Planning Studio → **Photo archive**, refresh and confirm the frame
   appears marked **TEST**. Its Sheet audit row should be present or, if logging
   failed, it should say **Sheet pending**.

## Two-device concurrency test

1. Open the **same generated rehearsal link** on two devices, each with its
   own anonymous Firebase UID, and confirm both see five available frames.
2. Capture one photo on Device A. After successful server confirmation,
   Device A should show four remaining. Device B refreshes its shared counter
   roughly every **15 seconds** while the camera is open (also on tab focus).
   It should display frame #01 as **sealed**, without downloading the image.
3. Take frames #02–#04, then make both phones attempt the final frame at
   approximately the same time. Only one server transaction should commit
   frame #05. The other upload should fail clearly without increasing the
   shared counter; neither user is granted a sixth frame.
4. Select **End test** in the planner; the backend should reject further test
   uploads. Starting a new rehearsal generates a new rehearsal identifier,
   so links issued in previous sessions cannot be reactivated.
5. Test an interrupted network connection and then recheck the server archive.
   A captured frame is not considered final until the Function confirms it.
   There is no reliable offline retry queue yet.

**Limitations:** The film strip uses a 15-second server poll, not a low-latency
Firestore listener. Two devices never synchronize camera orientation, aspect
ratio, filters or focus. The photo quota belongs to the invitation, not the
device. The website does not yet issue one distinct code per allotted seat.

## Cleaning up

Test photos are intentionally real Drive objects and real Firestore metadata;
**ending the rehearsal does not delete the photos**. Keep them clearly marked
`TEST_AJ_`, and remove them deliberately from Drive, Firestore test records
and Sheet after verifying audit relationships. Do not delete production
guest photos or edit the audit sheet while another test is in progress.

If anything fails, capture the exact guest error, the Firebase Functions error
code/log, and the Photo archive status. These identify whether the issue is
auth/App Check, invitation verification, Drive OAuth/CORS, storage permission,
transaction finalization or Sheet logging.
